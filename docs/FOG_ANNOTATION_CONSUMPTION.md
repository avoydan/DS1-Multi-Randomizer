# Fog annotation consumption audit

**Scope:** pinned DS1 FogMod path in the vendored source at `6e6dc78`, as called by `FogHost` and its progression commands. This is a source-level audit for replacing the runtime `dist/fog.txt` dependency. It distinguishes game facts from policy; it does not claim the replacement catalog has been authored yet.

## Architecture consequence

The replacement needs only the active semantic projection above. A single C# provider should compose typed project-owned policy with facts read from the verified pristine DSR root, validate all references, and adapt the result into a **fresh** `AnnotationData.Annotations` object per run. The adapter keeps the proven Graph/GameDataWriter code in place while removing YAML as the runtime architecture. Facts must not be inferred from the randomized staging directory.

The model's input order is part of the compatibility contract wherever FogMod iterates a list before seeded shuffles or chooses an indexed custom start. `Areas`, their `To` lists, `KeyItems`, entrance/warp lists, `CustomStarts`, and lot ranges must preserve authored order. Do not alphabetically sort lists merely to produce a canonical hash. The catalog fingerprint should use a versioned canonical encoding that preserves behavioral order, float values, conditions, tags and null/default distinctions; only sets proven unordered may be normalized.

The development oracle currently contains 131 areas, 27 key items, 15 warps, 109 entrances, 16 custom starts, 127 default costs, 392 enemy scaling rules, 440 lot starts and 108 default collision flags. These are scope measurements only, not values copied into the project model. They show why the production provider must combine game-derived indexing with compact authored policy instead of serializing the YAML as a new literal blob.

The audit exposes two existing non-FogMod consumers that also need migration before offline generation can be claimed: backend `fogItemRules.ts` parses `KeyItems` and `LotLocations` from `fog.txt`, and backend progression-model validation binds to the file's SHA-256. The upstream downloader remains in place until the new catalog has passed the reference comparison and cold-offline gates.

The same provider should expose a small versioned host projection for the backend's tracked item IDs, required flags and lot starts. This avoids a second copy of those rules in TypeScript and makes them available before combined item generation. Progression-model cache identity must move from the legacy annotation file digest to the catalog profile/fingerprint as one coordinated producer/consumer change; the old file digest must not be reused as the new catalog identity.

The fact index retains each `ItemLotParam` row and its non-empty item slots, plus every positive value in all five MSB treasure slots. It exposes slot 1 separately because the pinned SoulsFormats reader documents that only the first slot appears functional; it keeps slots 2-5 as audit facts and never uses them to derive item locations. Against the byte-verified clean map and GameParam set, the index finds 534 positive slot-1 references: 421 resolve to `ItemLotParam`, while 113 distinct IDs have no matching row. Nine positive values occur in slots 2-5. A development-only check confirms that none of those 113 unmatched IDs is in the pinned Fog oracle's active `LotLocations`; the reference reader therefore does not use them for item discovery, and they are not candidates for the project-owned item-location model. Production fact reading does not load the oracle. These orphan map facts remain preserved for audit and outside the consumed annotation model. In the verified QA copy, the geometric index retains 3,755 regions (2,123 Point, 1,191 Box, 177 Cylinder and 264 Sphere) and resolves unique part transforms for 427 of 558 treasure events and 407 of 534 slot-1 ItemLot references.

`FogDsrFacts.Read` can also take the clean DSR game directory and read item display names from its English FMG tables. This is used to identify item IDs from game facts rather than copying `KeyItems.ID` values; the real-data test confirms that goods `3:384` resolves to “Peculiar Doll”. Enemy facts now retain pristine MSB world transforms; a development audit uses them with spawn-region, boss-event, and nearby gate-object facts for area-boundary review. The fact reader still does not assign items to logical areas; that is project policy and requires the area/lot provider.

## Important limits

- This audit identifies what the current code reads; it is not proof that every read is used for every option profile.
- `GameDataWriter` contains an intentionally disabled collision-connect experiment (`Side.Col`); that field is excluded from the active catalog contract.
- Textual YAML parity is not a target. The comparer must normalize only active behavior fields and separately classify project-owned policy differences.
- No annotation field is considered complete until its provenance has category A, B, or C and its references validate against pristine DSR; unresolved category D values block release.

## Implemented validation foundation

`tools/fog-host/src/FogDsrFacts.cs` reads and verifies the supported external data root, then indexes the 17 pristine map files and pristine GameParam. It records object/entity IDs and transforms, collision play-region data, enemy parts and parameter IDs, region IDs, transforms and shape dimensions for Point, Box, Cylinder and Sphere regions, spawn-point references, treasure-part transforms and treasure-to-ItemLot references, the four item parameter tables, and ItemLot rows and contents. `FogDsrFacts.Validate` can check a typed catalog's area maps, entrance objects/action regions, warp destination entities, starts, enemy/collision references, lot IDs, and item IDs. `FogDsrFactsTest` verifies the index against the local QA data and validates a synthetic catalog built from indexed game facts, including rejection of a nonexistent start and synthetic entrance/warp sides whose project area omits the endpoint map. The development-only `tools/fog-reconstruction/AnnotationSemanticComparer.cs` reports category hashes and marks unreviewed differences unresolved. Its synthetic tests pass, but it has not been run against a complete project policy. This does **not** validate the reference annotations or a complete project policy: those references remain unverified until the project-owned catalog is authored and wired into the host.

`FogAnnotationPolicyResolver` now supplies two small fact-backed projections: key-item policy resolves a semantic item name plus English DSR name/category to a unique GameParam ID, and custom-start policy resolves a map plus spawn-region name to one unique spawn-point ID. Both keep authored order and fail on missing or ambiguous facts. A project-owned 16-entry custom-start policy now resolves named DSR spawn regions and validates as a partial catalog. Its location set, order, and owning area IDs match the development oracle exactly. All 16 start areas are declared as graph nodes and their spawn maps validate against pristine MSB facts. Six start-area records have complete consumed fields; ten still have unresolved static links. All 16 area tag and scaling-base fields now match the comparison reference. The Lost Izalith pre-lava `trivial` tag is a project rule anchored to the pristine spawn region, boss-defeat enemy, boss-room entrance region, and post-encounter wall objects; the reference is used only to confirm field parity. The provider is still not wired into production; complete key-item and lot-location policies are also missing. A fact-backed enemy-scaling resolver validates authored collision areas and included enemy names against pristine MSB facts and reports unassigned collision groups, but no complete enemy policy has been authored. A development-only comparison found 286 map/collision groups among treasure sources: 273 map to one reference area, 11 map to multiple areas and 2 have no reference-area annotation. These counts guide authored exceptions; the values were not added to production policy. A development-only query matched all 108 `DefaultFlagCols` entries to DSR collisions, but none of the boss flags equal the source `PlayRegionID` or `DisableBonfireEntityID`; all 108 source play-region IDs are below 10, so those MSB fields alone do not derive the flag association. `FogDsrFacts` now indexes direct positive `SetEventFlag` writes from the verified per-map and common EMEVD archives; the shared Darkroot MSB resolves to its owning `m12_00_00_00` event archive. Direct map-archive `SetEventFlag` scanning found same-map writers for 25/27 raw map/flag pairs (106/108 collision rows). This association is implemented and tested as project policy; see the C classification below. The dev-only spatial index supports box, cylinder, sphere and point containment for authored area-region analysis; geometric containment alone does not assign a game object to a Fog logical area. In the verified QA copy, a report covered 543 positive treasure slots: 412 have part transforms, 216 positioned references match no region volume, 72 match multiple regions, and one reference matches 10 regions; the remaining 124 positioned references each match one region. This confirms that region volumes are useful candidates but cannot replace authored per-area policy.
